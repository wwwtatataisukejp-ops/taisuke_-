# 01 仕入プレイブック

> 参照：02仕入部 全員 ／ 01市場リサーチ部 全員 ／ `roi-calculator`
> 前提：`00-sedori-basics.md` の数値基準・赤線を満たしていること。

---

## 1. 仕入判断の絶対順序

```
① 赤線チェック（法令・規約・真贋）  → 1つでも触れたら即 NO GO
② 相場の確定（売却実績の中央値）    → 出品価格ではなく「売れた価格」
③ 回転の確定（直近30日の成約件数）  → 何日で現金に戻るか
④ 利益の確定（手数料・送料込み）    → ROI・粗利率
⑤ 資金の確認（今その額を出せるか）  → 在庫比率70%以下
```

**②を飛ばして④を計算するのが最大の事故要因**です。
「出品されている価格」は誰も買っていない価格かもしれません。

## 2. 相場の取り方（全仕入エージェント共通手順）

| 手順 | 内容 | 注意 |
|---|---|---|
| 1 | 型番で完全一致検索する | 型番違い・世代違いを混ぜない |
| 2 | **売却済み**の実績だけを抽出する | 出品中の価格は相場ではない |
| 3 | 直近30日に絞る | 古い実績は現在の相場を表さない |
| 4 | 同一コンディション帯に絞る | 新品と中古Cを混ぜない |
| 5 | **中央値**を採る | 平均値は外れ値に歪められる |
| 6 | サンプル数を記録する | 3件未満は「相場未確定」として扱う |

### サンプル数による信頼度
| 直近30日の成約件数 | 扱い |
|---|---|
| 10件以上 | 相場として信頼できる |
| 4〜9件 | 参考値。回転日数を保守的に見積もる |
| 3件以下 | **相場未確定**。保留、または仕入額を半分以下に |
| 0件 | NO GO（需要が確認できない） |

### 記載フォーマット（必須）
```
相場 ¥12,800（直近30日 実績11件の中央値／2026/07/27時点／コンディション：中古良い）
```

## 3. 回転日数の見積り

```
想定回転日数 ≒ 30日 ÷ 直近30日の成約件数 × （自分より安い出品者数 + 1）
```

- 例：成約 11件/月、自分より安い出品者 3人
  → `30 ÷ 11 × 4 = 約11日`
- 出品者数が多い商品は、この式が急激に悪化します。**出品者数は回転の敵**。
- 算出後、`00-sedori-basics.md` の基準（45日以内／上限60日）で判定します。

### 回転が読めない場合の保守ルール
- 実績3件以下 → 回転日数は **90日** として計算（ほぼ NO GO になる）
- 季節商品でシーズン外 → 次シーズンまでの日数を回転日数に加算

## 5. 店舗仕入の設計（`store-sourcer` 用）

### 5.1 巡回ルートの組み方
1. **移動時間を先に固定**する（1日の移動時間は総稼働の30%以内）
2. 期待値の高い店から回る（過去の成果を店舗別に記録）
3. 同一エリアを固めて、移動距離を最小化する
4. 滞在時間の上限を店ごとに決める（例：中型店30分）

### 5.2 店舗別の狙い目
| 店種 | 狙う棚 | 狙う時間帯 |
|---|---|---|
| リサイクルショップ | ジャンク棚・入荷直後の未整理棚 | 開店直後 |
| 家電量販店 | 展示品・型落ち・在庫処分ワゴン | 週末・決算期 |
| 書店 | 専門書・図録・付録付き | 返品前の月末 |
| ホームセンター | 季節終わりの処分品 | シーズン切替時 |
| 総合スーパー | 棚替え時の値下げ | 改装前 |

### 5.3 値札の読み方（要ローカライズ）
店舗ごとに値下げの規則があります。**自分で観察して下表を埋めてください**。

| 店舗名 | 値下げのサイン | 値下げ周期 | 最終価格の目安 |
|---|---|---|---|
| （記入） | （例：黄色シール） | （例：2週ごと） | （例：定価の30%） |

### 5.4 現場での判断時間
1商品あたり**90秒**を上限とします。
90秒で判断できない商品は、写真だけ撮って「保留リスト」へ回してください。
現場で悩む時間が、他の棚を見る時間を奪います。

## 6. 電脳仕入の設計（`online-sourcer` 用）

### 6.1 利益の source を明確にする
| 手法 | 利益の源泉 | 注意点 |
|---|---|---|
| セール・クーポン | 情報差 | 転売目的購入を禁じる規約に注意 |
| ポイント還元 | 実質値引き | **ポイントは現金ではない**。ROIには本体価格で計上 |
| フリマの相場ズレ | 情報差 | 真贋・状態リスクが高い |
| 販路間の価格差 | 場所差 | 手数料差を必ず引いてから比較 |
| セット崩し・セット組み | 手間差 | 作業時間を経費として計上 |

### 6.2 ポイント還元の扱い（重要）
ポイントを利益に含めると、**現金が回らないのに黒字に見える**という事故が起きます。

```
ROI計算 : ポイントは含めない（本体支払額で計算）
別枠管理 : 「獲得ポイント」として台帳に別記録
```

ポイント込みでしか基準を満たさない仕入は、`cashflow-planner` の確認を取ってください。

### 6.3 電脳仕入のリスクチェック
- [ ] 出品者の評価数・評価率を確認したか
- [ ] 画像が使い回し（メーカー公式画像のみ）ではないか
- [ ] 相場より極端に安い理由が説明できるか（説明できない安さは偽物・欠品を疑う）
- [ ] 追跡付き配送か
- [ ] キャンセル・返品の可否を確認したか

## 7. 卸・問屋仕入の設計（`wholesale-negotiator` 用）

### 7.1 卸取引が向く条件
- 継続的に同じ商品が売れている（実績データがある）
- ロットを捌ける回転がある
- 保管スペースと資金に余裕がある

**単発のせどりで基準を満たせない商品を、卸で大量に買っても解決しません。**

### 7.2 交渉の準備物
| 準備物 | 目的 |
|---|---|
| 古物商許可証の写し | 事業者であることの証明 |
| 想定発注ロット・頻度 | 相手のメリットを示す |
| 販売実績（月間販売数） | 信用の裏付け |
| 支払条件の希望 | 前払／掛け／締め日 |

### 7.3 交渉で必ず確認する5項目
1. 掛け率（定価に対する仕入率）と**ロット別の変動**
2. 最低発注金額・最低ロット
3. 支払条件（前払 / 掛け何日）と**キャッシュへの影響**
4. 返品・不良品の扱い
5. **販路の制限**（Amazon不可・価格維持要請の有無）

5番は特に重要です。仕入れた後に「その販路では売れない」と判明する事故を防ぎます。

## 8. 海外仕入の設計（`overseas-buyer` 用）

### 8.1 コスト構造（国内仕入との違い）
```
総原価 = 商品代金 + 国際送料 + 関税 + 消費税 + 通関手数料
        + 為替手数料 + （必要なら）国内転送費
```

**国際送料と関税を入れずに ROI を出すのは計算間違い**です。

### 8.2 必ず確認する項目
| 項目 | 確認先 | 未確認時の扱い |
|---|---|---|
| 輸入可否（規制品でないか） | 税関・所管省庁 | 保留 |
| 技術基準適合（無線機器） | 電波法（技適） | NO GO（未適合品の販売は不可） |
| 電気用品の表示 | 電気用品安全法（PSE） | NO GO |
| 食品・化粧品・医薬品該当性 | 食品衛生法・薬機法 | `law-checker` に必ず回す |
| 商標・並行輸入の可否 | 権利者・販路規約 | `law-checker` に必ず回す |
| 関税率 | 品目別の税率表 | 保守的に高い方を採用 |

**海外仕入は `law-checker` の判定を通すまで GO を出してはいけません。**

### 8.3 為替とリードタイム
- 為替は**仕入時ではなく決済時**のレートで確定します。保守的に見積もってください。
- リードタイム（発注〜受領）は回転日数に**そのまま加算**します。
  例：船便45日 + 販売30日 = 回転75日 → 基準（60日）超で原則 NO GO

## 9. 仕入をやめるべきサイン（全エージェント共通）

以下に1つでも当てはまったら、**その場で NO GO** にしてください。

1. 相場の根拠が「出品価格」しかない
2. 直近30日の成約実績が0件
3. 真贋・許可・規約のいずれかが「不明」のまま
4. 数字を1つでも「たぶん」で埋めている
5. 在庫比率が70%を超える
6. 「安いから」以外に仕入理由を言語化できない
7. 1回の仕入額が¥50,000超（→ 社長へエスカレーション）

---

## 10. 仕入後の引き継ぎ

仕入が確定したら、以下の順で次の担当へ渡します。

```
仕入確定 → `authenticity-checker`（必要時）→ `condition-grader`
        → `pricing-strategist` → 出品パイプライン（P2）
        → `inventory-manager`（在庫台帳へ登録）
        → `bookkeeper`（仕入計上・レシート保管）
```

**`inventory-manager` と `bookkeeper` への引き継ぎ漏れが、
月末の在庫不一致と記帳漏れの最大原因です。**
